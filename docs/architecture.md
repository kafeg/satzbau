# Архитектура

Документ описывает, как устроено приложение целиком: что откуда берётся, что считается,
что хранится и что из этого может сломаться. План работ — `plan.md`.

## Общая схема

```
источники в сети (1,4 ГБ)
        │
        │  tools/build_data.py            на машине разработчика, вручную, редко
        ▼
content/build/*.json  +  sources.lock     ≈300 КиБ, КОММИТИТСЯ в репозиторий
        ▲
        │  content/manual/*.yaml          темы, шаблоны, объяснения — пишутся руками
        │
        │  vite build                     в GitHub Actions
        ▼
   dist/ → GitHub Pages                   статика, никакого бэкенда
        │
        ▼
   браузер / PWA на домашнем экране
        ├── ядро: парадигмы → морфология → генератор → разбор
        ├── повторы: ts-fsrs
        └── IndexedDB: журнал ответов + производное состояние
```

Две вещи, которые надо понимать про эту схему:

⚠️ **Собранные данные коммитятся.** Это не нарушение правила «сырые дампы не коммитим»:
не попадают в репозиторий именно дампы источников, 1,4 ГБ. А собранный компактный JSON —
это и есть тот результат, который лицензирован под CC BY-SA 4.0, и без него нечего собирать
и публиковать. Иначе GitHub Pages пришлось бы качать гигабайт при каждом деплое.

⚠️ **Сборка данных и сборка приложения — разные вещи, с разной частотой.** `build_data.py`
запускает человек, когда хочет обновить данные; результат коммитится и ревьюится как обычный
диф. `vite build` запускается в CI на каждый push и данные не трогает.

## Слои и границы

| слой | где | знает о | не знает о |
|---|---|---|---|
| сборка данных | `tools/*.py` | формате источников, чистке, лицензиях | приложении |
| данные | `content/` | — | — |
| парадигмы | `src/core/paradigms/` | закрытых таблицах немецкого | словах, заданиях, UI |
| морфология | `src/core/morph/` | как из записи вывести форму | заданиях, UI |
| генератор | `src/core/generator/` | шаблонах, подборе слова, дистракторах | UI, повторах |
| разбор | `src/core/explain/` | как объяснить ошибку по-русски | UI |
| повторы | `src/core/srs/` | FSRS, двух видах карточек | содержании заданий |
| хранилище | `src/store/` | IndexedDB, журнале, экспорте | грамматике |
| экраны | `src/app/` | всем перечисленным | источниками данных |

Правило границ: **ядро не знает про React и про IndexedDB.** Генератор — чистая функция
от данных и состояния. Это нужно не ради красоты, а чтобы валидатор заданий мог прогнать
все шаблоны на всех словах в тесте, без браузера.

## Данные

### Что лежит в репозитории
```
content/
  manual/           пишется руками, YAML
    themes.yaml       темы: слово → тема, уровень, порядок внутри темы
    templates.yaml    шаблоны заданий
    explain.yaml      объяснения: один текст на правило
    fixes.yaml        ручные правки: 6 пар управления, род у омонимов, слоты без падежа
  build/            собирается скриптом, коммитится
    nouns.json  verbs.json  adjs.json  sentences.json
    sources.lock      дата и SHA-256 каждого источника
```
Схемы `build/*.json` — в `data.md`, они замерены на реальных дампах.

### Сборка
`tools/build_data.py`: скачать → распарсить → почистить → отобрать по `themes.yaml` →
применить `fixes.yaml` → записать компактный JSON → записать `sources.lock`.

`tools/check_data.py`: валидация собранного. Не «есть ли файл», а инварианты:
у каждого существительного есть род или флаг `pl_only`; у каждого глагола выводится полное
спряжение; каждое слово из `themes.yaml` попало в выход или объяснено в отчёте; каждая
ссылка `why` из шаблона существует в `explain.yaml`.

## Ядро: как рождается задание

```
шаблон  ──need──▶  подбор слова (тема, уровень, требования, состояние повтора)
   │                        │
   │                        ▼
   └──answer──▶  парадигма + морфология  ──▶  верный ответ
                            │
                            └──▶  дистракторы: те же формы в других падежах и родах
                                          │
                                          ▼
                              проверка: все варианты различны
```

Шаблон (`content/manual/templates.yaml`), настоящий:
```yaml
- id: prep-dat-mit
  rule: prep-dativ            # единица повтора и ключ объяснения
  level: A1
  kind: choice
  frame: "Ich fahre mit {slot} {w}."
  need: {pos: n, theme: transport, tags: [vehicle], not: [pl_only]}
  slot: {paradigm: def_article, case: dat, num: sg, prep: mit}
  options: {paradigm: def_article, count: 4}
  why: prep-dativ
```
⚠️ Предлог лежит в данных (`prep: mit`), а не вычитывается из рамки: его подставляет
объяснение, и вытаскивать его регуляркой из фразы — верный способ однажды промахнуться.

**Задания не хранятся.** Сорок шаблонов на лексиконе из тысячи слов — это десятки тысяч
заданий из нескольких десятков килобайт. Добавить тему — значит добавить слов, а не заданий.

Размер лексикона: он равен объёму `themes.yaml`, то есть при 20 темах по 60–100 слов это
примерно 1200–2000 лемм на все части речи, а не 1546 одних существительных, как в замерочном
прототипе. Бандл от этого только меньше.

Два ограничения, которые держат конструкцию простой:

- **один слот на шаблон.** Два пропуска в одной фразе дают комбинаторику в валидаторе
  и неоднозначную оценку «что именно он не знает». Нужны две фразы — пишем два шаблона;
- **условия в `need` — закрытый список**, а не язык запросов: часть речи, тема, теги,
  род, наличие поля (`pl`, `gen`, `pp`), отрицание по флагу (`aux_hs`, `pl_only`).
  Новое условие добавляется только тогда, когда без него нельзя написать нужный шаблон;
- **теги обязательны.** Темы слишком грубые, чтобы фраза не теряла смысл: `Ich fahre mit dem
  Kühlschrank` грамматически безупречно и бессмысленно. Поэтому шаблон требует `tags: [vehicle]`,
  а словарь тегов закрыт (`content/manual/README.md`);
- **прилагательное в шаблоне фиксировано**, меняется существительное: иначе получается
  `eine kleine Anmeldung`.

### Что ядро нашло в данных
Ядро — не только код, но и проверка контента. Что оно вскрыло на первых десяти шаблонах:

- **«Ich brauche …» — это не правило о предлогах.** Падеж здесь требует глагол, предлога
  во фразе нет вообще. Появилось отдельное правило `akkusativ-objekt` со своим объяснением,
  а `prep-akkusativ` получил настоящую рамку с `für`;
- **«Die Lampe steht in dem Zimmer» грамматически верно, но по-немецки так не говорят** —
  обязательно `im`. Тренировать падеж на форме, которой носитель не употребляет, нельзя,
  поэтому у Wechselpräpositionen предлог теперь `auf`: он с артиклем не сливается;
- **«Ich habe die Wohnung geschlafen»** — рамка задаёт объект, а `state` берёт и непереходные
  глаголы. Понадобился тег `obj`. И его оказалось недостаточно: «die Wohnung gekocht» —
  глагол переходный, но этот объект не берёт. Отсюда тег `housework`;
- **«Ich brauche ein Benzin»** — неисчисляемые не употребляются с неопределённым артиклем.
  Решение `mass` в `fixes.yaml`;
- **«für den Nachbaren»** вместо `Nachbarn` — родительный у n-Deklination нельзя выводить
  правилом, он теперь всегда пишется в данные;
- **у слияний ответ был постоянным.** `merge-wo-in` с родами m и n всегда даёт `im`:
  человек отвечает не глядя. Нужен парный шаблон на `wohin` → `ins`.

Вывод, который стоит помнить: **задания надо читать глазами**, и это часть этапа, а не
проверка «на всякий случай». Тесты ловят однозначность и выводимость, но не бессмыслицу.

### Второе слово: что из этого вышло
Шаблон привязан к одному слову, и глагольные рамки от этого безобъектные: «Er kocht oft».
Второе слово (`fill2`) добавлено, но результат оказался не тем, что ожидался.

⚠️ **Глагольные рамки с объектом проверены и отвергнуты.** Собиралось «Er kocht das
Wohnzimmer», «Er würzt das Salz», «Gestern habe ich die Tür geschlafen». Тег `obj` говорит
«переходный», а не «берёт ИМЕННО такой объект», и никакой набор тегов этого не скажет:
немецкий глагол выбирает объект по смыслу. Чтобы было иначе, нужны списки объектов
на каждый глагол — это другая работа и другие данные.

**С прилагательным вышло.** Оно согласуется с существительным грамматически, а не по
смыслу, поэтому пара собирается правилом. Но и тут потребовалось сузить: «die pünktliche
Ampel» и «das schnelle Benzin» тоже собирались, отсюда тег `generic` — прилагательные,
подходящие к любому предмету.

Первым словом в таких шаблонах стоит существительное, прилагательное приходит вторым:
заданий тогда 141, а не 10, и повторами отслеживается род существительного — то, что
и надо выучить.

### Задание восстанавливается из пары «шаблон + слово»
Порядок вариантов засеян идентификатором шаблона и словом, поэтому `generate(t, w)` всегда
даёт побайтово то же задание. Второе слово выводится оттуда же, поэтому пары в журнале
по-прежнему достаточно — третье поле не понадобилось. На этом стоит весь журнал: хранить достаточно пары, а задание
со всеми подстановками пересобирается при показе. Иначе экран «мои ошибки» не смог бы
подставить `{prep}` в строку правила — в журнале подстановок нет.

⚠️ Это не удобство, а несущее свойство: сломается детерминизм — сломается журнал.
Проверяется тестом на всех шаблонах и всех словах.

### Что вычисляется, а не хранится
Артикли и местоимения; окончания прилагательных по трём склонениям; слияния предлога с артиклем;
полное спряжение из `p3`, `pt`, `pp`, `aux`; склонение существительного из `g`, `pl`, `gen`,
`dpl`, `nd`; дистракторы.

### Правило однозначности
Задание спрашивает **форму по известному падежу**, а не падеж по форме. Причина: в немецком
формы совпадают (`das` — и Nominativ, и Akkusativ; `den` — и Akkusativ единственного,
и Dativ множественного), и вопрос «какой это падеж» часто не имеет одного ответа.

Исключение — упражнение на слияния: `im` однозначно `in` + Dativ, и именно поэтому его
можно спрашивать в обе стороны.

⚠️ Отсюда обязательный инвариант генератора: **среди вариантов ответа верный ровно один,
и все варианты — разные строки.**

Первая версия правила дистракторов — «то же слово в других падежах» — этого не выдерживает.
Для женского рода определённый артикль даёт Nom `die`, Akk `die`, Dat `der`, Gen `der`:
в наборе два дубля и два правильных ответа. Поэтому **варианты берутся из инвентаря форм
парадигмы**: все различные формы определённого артикля — это `der`, `die`, `das`, `den`,
`dem`, `des`, и генератор выбирает верную плюс три других, предпочитая те, что были бы
верны для этого же слова в других падежах. Валидатор проверяет это на всех парах
«шаблон × слово», а не в рантайме у пользователя.

## Язык задания и перевод
Фраза задания — немецкая. Полного русского перевода фразы **нет**, и это следствие данных,
а не экономия: в лексиконе русский хранится одной формой в именительном (`Zug` → «поезд»),
а во фразе нужен другой падеж — «Я еду на поезде». Склонять русские слова приложение не умеет
и учиться не будет.

Поэтому под фразой показывается **перевод слова, а не фразы**: `der Zug — поезд`. Русский
работает там, где он сильнее всего — в объяснении правила, которое написано руками и
сопоставляет падежи напрямую.

Полные переводы фраз появляются только там, где достались бесплатно: примеры из Tatoeba
на карточке слова, у них перевод уже есть.

⚠️ Это расходится с макетом дрилла, где под немецкой фразой стоит её полный перевод.
Макет в этом месте предполагал данные, которых нет. Поле `ru` в шаблоне остаётся
на случай фраз с фиксированным наполнением, где перевод можно написать руками.

## Разбор ошибки
Объяснение собирается из трёх частей: текст правила из `explain.yaml` (один на правило),
подставленные значения задания, и **чем был ответ пользователя** — для этого ядро умеет
обратный разбор: по введённой форме сказать, какой это падеж, род и число.

Обратный разбор неоднозначен по своей природе, поэтому он возвращает список, а объяснение
берёт самый частый для этого уровня вариант: `kleine` → «Nom/Akk женского рода»,
как в макете разбора.

⚠️ Границы честности: для ввода окончания разбор часто даёт слишком много вариантов — `-en`
встречается почти везде. Правило: **«чем был твой вариант» показываем только если разбор дал
один или два варианта** для этого слова в этом контексте. Иначе показываем только верный путь
и не выдумываем объяснение ответу, которого не понимаем.

## Повторы
Две сущности с состоянием FSRS:

| карточка | ключ | зачем |
|---|---|---|
| `rule` | id правила (`prep-dativ`, `adj-dat-en`) | расписание повторов строится по ней |
| `word` | лемма | подбор наполнения: слабое слово всплывает чаще |

Один ответ задевает обе. Оценки: верно с первого раза → `Good`, неверно → `Again`,
верно после «не знаю, покажи правило» → `Again` для правила и `Hard` для слова.
Оценок `Easy` на старте нет: мы не измеряем скорость и не будем притворяться, что измеряем.

Библиотека — `ts-fsrs` (MIT), версия 6: новый `DefaultScheduler` (FSRS-7), создаётся
асинхронно один раз на запуск. Старый `fsrs()`/`Card` в шестёрке помечен устаревшим.

Две мелочи библиотеки, зафиксированные в коде: типы входа и выхода планировщика не сходятся
по полю `stabilityFast`, а `cardId` он генерирует случайным — мы подменяем его своим ключом,
иначе два проигрывания одного журнала дают разные объекты и состояние нечем сравнить.

## Хранилище
IndexedDB, **одно** хранилище:

- **`answers`** — журнал, только добавление: время, шаблон, правило, слово, верно или нет,
  что именно ответил, смотрел ли правило до ответа. Источник истины и он же файл экспорта.

⚠️ Поправка к первоначальной записи: хранилища `state` нет. Состояние повторов
проигрывается из журнала при загрузке и после каждого ответа — один ответ это два вызова
планировщика, на тысячах ответов это миллисекунды. Так состояние физически не может
разойтись с журналом, и кэш появится не раньше, чем пересчёт станет заметен.

Почему так: экспорт и импорт — это просто журнал; формат производного состояния можно
менять в любой версии, пересчитав его; «починить прогресс» всегда возможно.

Три следствия, которые надо заложить сразу:

- ⚠️ **пересчёт из журнала не обязан дать те же числа.** FSRS зависит от своих параметров
  и версии алгоритма; если `ts-fsrs` обновится, пересчёт даст немного другое состояние.
  Это терпимо — состояние производное, — но в журнале пишем версию и параметры, чтобы
  расхождение было объяснимым, а не загадочным;
- **неизвестные идентификаторы игнорируются.** Слово или правило могут исчезнуть при
  обновлении данных: состояние их просто не строит, а журнал сохраняет как было;
- **у данных есть версия.** `content/build` меняется — меняется и хэш в манифесте, иначе
  service worker продолжит отдавать старые данные. Обновление данных пользователь видит
  и подтверждает в настройках.

Цена: журнал растёт. Прикидка: 60 байт на ответ, 100 ответов в день — 2 МиБ за год.
Приемлемо; если станет много, старые записи сворачиваются в агрегат, но не раньше.

## Офлайн и PWA
- **примеры предложений грузятся отдельно и лениво**: 46 КиБ gzip нужны одному экрану
  («новые слова темы»), и висеть на старте они не должны. В precache они всё равно
  попадают, поэтому офлайн работает;
- service worker кэширует оболочку приложения и `content/build/*.json` при установке:
  после первого открытия приложение работает без сети целиком. Замерено на собранной версии:
  16 записей в precache, у каждого файла данных свой `__WB_REVISION__`, так что смена данных
  сама себя инвалидирует. Проверка была не «кэш есть», а жёсткая: сервер остановлен,
  страница перезагружена — приложение открылось и задания собрались;
- `navigator.storage.persist()` запрашивается после первого осмысленного действия,
  а не на старте;
- обновление данных — новая версия service worker, **молча**: `registerType: 'autoUpdate'`.
  Первоначальная запись обещала «явное обновить в настройках», но это дороже и ничего
  не даёт: данные и код едут одной версией, и выбор «остаться на старых данных» человеку
  не нужен. Пересмотреть, если обновление когда-нибудь начнёт терять прогресс;
- ⚠️ **на iOS хранилище PWA может быть вытеснено**, если приложением не пользоваться.
  Поэтому экспорт прогресса в файл — не роскошь, а страховка, и приложение должно о ней
  напоминать. Это надо проверить на устройстве, а не прочитать в документации;
- ⚠️ **немецкий голос Web Speech на iOS не проверен.** Если голоса нет — кнопка озвучки
  скрывается, а не молчит. Проверять вместе с офлайном.

## Публикация
Vite собирает статику, GitHub Pages раздаёт её **из GitHub Actions**, не из ветки:
в корне репозитория лежит исходник, а не собранный сайт.

⚠️ Поправка к первоначальной записи «Pages: Deploy from a branch, main / root» — так нельзя:
проект со сборкой либо коммитит `dist` в ветку, либо деплоит артефактом из Actions.
Второе чище: в репозитории нет собранного кода.

Приложение живёт по адресу с подпапкой (`/satzbau/`), поэтому `base` в конфигурации Vite
задан, а маршрутизация — по хэшу: Pages не умеет отдавать `index.html` на произвольный путь.
Маршруты: `#/` — главная, `#/t/<тема>` — экран темы, `#/drill/<правило>/<тема>` — тренировка
(любая часть может быть пустой или `-`: без правила и темы это всё вперемешку).
Роутер свой, тридцать строк: библиотека тут дороже задачи.

Сборка и деплой — `.github/workflows/pages.yml`: `npm ci`, `npm run check`, `npm run build`,
артефакт из `dist`. ⚠️ В настройках репозитория Pages → Source должен стоять «GitHub Actions»,
иначе workflow проходит, а сайт не меняется.

## Стек и его границы
TypeScript + Vite + React. Стилей-фреймворка нет: токены из `design.md` ложатся в CSS-переменные
один раз, дальше обычный CSS. Состояние — один модуль-стор, без библиотеки: экранов восемь,
а не восемьдесят.

Критерий пересмотра: размер бандла и скорость холодного старта на iPhone в офлайне.
Если React не оправдает своего веса — меняем на Preact или уходим в ваниль, но не раньше,
чем это будет измерено на устройстве.

Замер на Э4 (шесть тем, 573 слова, десять шаблонов):

| что | как есть | gzip |
|---|---|---|
| JS (React + ядро + экраны + ts-fsrs) | 286 КиБ | 91 КиБ |
| CSS | 4,1 КиБ | 1,4 КиБ |
| данные, семь файлов | 109 КиБ | 25 КиБ |
| примеры предложений, отдельно | 169 КиБ | 46 КиБ |
| всё в precache | 608 КиБ | — |

React — больше половины JS, `ts-fsrs` добавил 14 КиБ gzip, ядро и экраны вместе дают
около 20 КиБ. То есть вопрос «React или ваниль»
на устройстве будет стоить примерно 55 КиБ gzip, и решать его надо по холодному старту,
а не по этой цифре.

## Чего в архитектуре нарочно нет
- **Графа предпосылок модулей** — правил пятнадцать, и порядок на главной сейчас просто
  порядок написания шаблонов. Граф уже нужен, но это отдельная работа по данным;
- **синхронизации и сервера** — экспорт файлом закрывает перенос между устройствами;
- **разбора предложений** — поэтому нет и упражнения «собери предложение из плиток»;
- **генерации объяснений** — они пишутся руками, и это главная ценность приложения,
  а не то, что надо автоматизировать.
